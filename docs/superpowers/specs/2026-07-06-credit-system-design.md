# 积分系统设计(纯充值制)

## 1. 背景

系统正在为上线做多租户准备(Beta 底座已合入 `master`:`Tenant`/`TenantMember`/`BetaCreditAccount`/`UsageLedger`,reserve→commit/refund、幂等、402 门禁已跑通)。公司要求输出一套对外收费的积分方案。

成本侧已核实的事实:

| 项 | 事实 | 来源 |
|---|---|---|
| 灰豚企业版 | 100 元/月(优惠通道),笔记搜索 3000 次/天(每次前 3000 条),笔记详情 1500 次/天,全局搜索 3000 次/月,笔记监测 2500 次/月,多设备同时登录 1 台,子账号 5 个 | 用户提供的官方套餐截图(2026-07-06) |
| 灰豚单次搜索成本 | ≈ 0.0015 元 | 100 元 ÷(3000×30×75%) |
| AI 文本 | gpt-5.5 走自有中转,成本 = 官方价 × 15%(1.5:10) | 用户确认 |
| AI 图片 | RunningHub,RH 币按运行时长扣(≈1.3 币/分钟,1 币 ≈ 0.0023 元)+ 低价渠道 0.1 元/次;实测单张 ≈ 0.11 元 | RunningHub 用量记录截图(24 条:52 币 + 1.2 元 / ≈12 张) |
| RunningHub 并发 | 最高档(专业版 Plus,169 元/月)并发也只有 5;当前免费版更低 | RunningHub 套餐截图 |

已确认的商业决策(用户拍板):

- 对外收费,纯充值积分制(非套餐订阅)。
- 只对产生真实外部成本的动作扣分;浏览、草稿编辑、发布、任务管理等全部免费。
- 免费额度:注册赠送一次性小额积分。
- 积分有效期:暂不设计,本版不实现。
- 定价数字由公司高层最终拍板,本 spec 给基准值和依据。

## 2. 目标

- 采集链路(note.searchV2)接入计量——当前零计量,是最大缺口。
- 建立单一积分池 + 每动作扣分表,复用现有 reserve/commit/refund 机制。
- 建立平台级「上游日闸门」与租户日限,防止共享灰豚额度被挤兑。
- 图片生成接入全局并发队列,适配 RunningHub 并发 5 的物理上限。
- AI 成本按官方价锚定记账,支持月度校准。

## 3. 非目标

- 不接支付网关(Beta 阶段管理员手动上分,收款线下;正式 SaaS 再接)。
- 不做积分有效期/过期清理。
- 不做发票、订单、退款流程。
- 不删除现有五个 beta bucket 的机制(向后兼容,见 7.4)。
- 不做 5 子账号轮换或多灰豚账号池(撞既有红线)。
- 不把供应商名(灰豚/huitun/RunningHub)暴露给普通用户。

## 4. 积分模型

### 4.1 基准

- **1 积分 = 0.1 元**(建议值,公司可调;代码中积分与人民币无绑定,只是定价口径)。
- 单一积分池:每租户一个 `credits` bucket,不再按功能分池。

### 4.2 扣分表(CREDIT_COSTS)

| action_key | 动作 | 扣分 | 成本依据 |
|---|---|---:|---|
| `note_search` | 笔记发现(一次搜索 run,≤100 条) | 2 | 上游 0.0015 元;定价实为 3000 次/天配给 |
| `note_detail` | 笔记详情补全(每条,预留,验证 ready 后启用) | 3 | 日池 1500,比搜索稀缺一倍 |
| `ai_text` | AI 文本(改写/生成/评分,每次) | 2 | 官方价典型 2k in/1k out ≈ 0.09 元,P90 留余量 |
| `image_generation` | AI 图片(每张) | 5 | 实测 0.11 元/张,毛利 ~70% |
| `analysis_report` | 分析报告(每份) | 10 | 复合动作(多搜索 + LLM 长输出) |

内容库单篇系统分析使用 `feature_key=note.system_analysis`,映射 `ai_text`,固定 **2 积分/条**。`analysis_report=10` 只用于完整分析报告的生成或重跑,不用于单篇笔记分析。

扣分为固定值,**不按 token/时长浮动**。上游波动(RH 币 2~7、token 长短)由毛利吸收,不传导给用户。

### 4.3 免费动作

浏览内容库/候选列表、草稿编辑、发布、定时任务、账号矩阵、任务中心查看——一律不扣分、不记 ledger。

### 4.4 注册赠送

注册即建租户时发放一次性 **100 积分**(建议值),复用现有 `_ensure_beta_credit_accounts` 位置改为发放 `credits`。赠送与充值在 ledger 上以 `feature_key` 区分(`grant.signup` / `grant.recharge`),便于营销费用核算。

## 5. 双闸门(防挤兑,核心机制)

纯充值积分不过期,已售积分总量会持续累积,理论可集中兑付,远超上游物理容量。双闸门是必选项:

### 5.1 平台日闸门(新表 `provider_daily_usage`)

```text
id
usage_date        # 上海时区自然日
endpoint_key      # note.searchV2 / note.detail / ...
used              # 原子自增
cap               # 当日上限,来自配置
created_at / updated_at
UNIQUE(usage_date, endpoint_key)
```

- **标称额度未实测**:3000/天、1500/天来自官方套餐页,真实可达吞吐(供应商频控/风控影响)未验证。
- 初始上限 = 标称 × 20%:搜索 **600/天**、详情 **300/天**;实测爬坡 2~4 周后逐步上调,终值不超过标称 × 75%(搜索 2250/天、详情 1125/天,留 25% 给重试、系统任务、风控波动)。
- 爬坡期间记录每日实际成功/失败率与错误码;出现供应商侧限频信号(异常错误码、连续失败)立即回退上一档,不硬顶。
- cap 放 `config/` YAML,不写死代码;调档改配置,不改代码。
- 打满时对用户报:**「数据源今日额度已用尽,明日 0 点恢复」**——不出现供应商名,失败就失败,不兜底。
- 检查与自增必须原子(UPDATE ... WHERE used + n <= cap 模式),失败即拒绝。

### 5.2 租户日限

- 默认 **50 次搜索/天/租户**(管理员可按租户调整),防单租户吃光全平台日额度。
- 实现:按 `usage_ledgers` 当日该租户 `note_search` reserve 计数,或独立轻量计数表;取实现简单者。

### 5.3 扣分顺序

```text
① 租户积分余额检查+reserve(不足 → 402,现有文案机制)
② 租户日限检查(超 → 429「今日获取次数已达上限」)
③ 平台日闸门原子占用(满 → 上述数据源额度文案,refund ①)
④ 调上游 → 成功 commit / 失败 refund + 释放闸门占用不回滚(闸门按尝试计,防重试风暴)
```

## 6. 图片并发队列

RunningHub 并发上限 5(最高档),这是物理墙:

- 全局信号量 = 已购并发数 − 1(留 1 给重试/管理员),值放 YAML。
- 图片任务统一入队(现有任务中心异步模型);积分在**入队时 reserve**,成功 commit、失败/超时 refund。
- 排队反馈:「排队中,前面还有 N 个任务,预计 X 分钟」(N × 3min 估算)。
- 队列深度上限(默认 20),超限才拒绝:「当前生成任务较多,请稍后再试」。
- 与多租户 Sprint 2 规划(每 user 并发 1、每 tenant 并发 2)拼合,不重复造轮子。

## 7. AI 成本核算规则

### 7.1 官方价锚定原则

积分定价按「官方牌价 + 毛利」设计,保证 100% 走官方渠道也不亏;中转 85% 差价是利润缓冲,不是定价基础。中转出事只影响利润厚度,不需要改价。

### 7.2 用量记账

- AI 调用完成时把 `{input_tokens, output_tokens, model}` 写入 `UsageLedger.request_summary`(字段已存在,当前未填)。
- 图片任务写入 `{rh_coins, duration_seconds, wallet_fee}`(能从 provider 响应拿到多少写多少,拿不到不编造)。

### 7.3 月度校准

```text
理论官方成本 = Σ(tokens × 官方单价)
校验1:中转实际账单 ≈ 理论官方成本 × 15%(偏离大 → 比例变了或统计漏了)
校验2:每 action 积分收入折算 ≥ 理论官方成本(官方价保本线)
```

### 7.4 新动作定价公式

```text
扣分 = ceil(该动作 P90 官方成本 / 0.1 元),向上取整到好记的数(1/2/3/5/10)
```

用 P90 不用平均,长尾贵请求不亏。

## 8. 与现有机制的关系

### 8.1 复用(不改)

- `UsageQuotaService` 的 reserve/commit/refund/adjust、幂等键、402 结构、原子扣减。
- `UsageLedger` 表结构(无 schema 变更)。
- 租户模型与注册建租户流程。
- 前端 usage balance 展示(新 bucket 自动出现)。

### 8.2 修改

- `usage_quota_service.py`:新增 `credits` bucket 与 `CREDIT_COSTS` 表;`BUCKET_LABELS` 加「积分」。
- `data_acquisition_service.create_note_search_run`:入口按 5.3 顺序接入扣分与闸门(当前零计量)。
- `backend/app/api/ai.py`、`drafts.py`、图片生成入口:bucket 从各自分池切到 `credits`,金额查 `CREDIT_COSTS`。
- AI/图片完成回调:补写 request_summary 用量。

### 8.3 兼容策略(现有 beta 租户)

- 现有五个 bucket(image_generation/ai_rewrite/text_action/draft_score/analysis_report)的账户数据不删除。
- 切换后新扣费一律走 `credits`;旧 bucket 余额由管理员用 `adjust` 一次性折算并入 `credits`(折算比例:按各动作扣分表换算),折算动作记 ledger。
- 不做自动双轨扣费(先旧后新),避免复杂度。

### 8.4 新增

- `provider_daily_usage` 表 + 服务(原子占用、查询)。
- 一条 Alembic migration。**提交前必须 `alembic heads` 确认单 head**(迁移链有过 merge head 历史)。
- `config/` 新增闸门与并发配置段(caps、tenant 日限默认值、图片全局并发、队列深度)。

## 9. 运维约束(必须写进部署文档)

1. 灰豚企业号「多设备同时登录 = 1 台」:该账号**专供服务端**,任何人再登网页版可能踢掉服务端会话,导致全平台采集报错。5 个子账号留给团队人工查数,不进服务端自动链路。
2. 账号被封/被踢应急:预留备用账号预算(报告表 1,100~360 元/月口径);切换动作是换 cookie 配置,不是改代码。客户侧由 reserve/refund 机制天然兜底(失败退积分)。
3. 对灰豚的请求保持**串行 + 最小间隔**(沿用既有低频串行红线);并发打向单账号既触发风控也无法提升有效吞吐。
4. RunningHub 当前是免费版,并发不足以支撑多租户;上线前需购买付费档(基础版 69/月起,并发 2;专业版 Plus 169/月,并发 5),购买档位由公司定,并发配置随之调整 YAML。
5. 单灰豚企业号容量 ≈ 200 个活跃付费租户,**为标称口径推算值**;正式容量承诺以爬坡实测为准。逼近上限时扩容路径是与供应商谈更高配额,不是堆账号。

## 10. 失败与文案原则

- 失败就失败,明确报错,不自动兜底、不静默降级(既有红线)。
- 普通用户文案不出现:灰豚、huitun、RunningHub、extData、connector、内部接口。
- 管理员/调试模式可见内部错误码、endpoint key、闸门状态。

## 11. 测试策略

- 单元:CREDIT_COSTS 扣分正确;reserve→commit/refund 走 credits;日闸门原子性(并发占用不超 cap);租户日限;旧 bucket 折算并入。
- 集成:note_search run 全链路扣分;闸门打满报数据源文案且积分已退;图片入队 reserve/出队 commit/失败 refund;402/429 结构。
- 回归:现有 beta 门禁测试(`test_beta_security_foundation.py`)不破坏。
- 验证命令:`python -m pytest tests/backend`;前端 `npm run build`;`alembic heads` 单 head。

## 12. 开发闸门

1. 本 spec 依赖数据获取阶段 1(note.searchV2 链路)已在开发;积分接入点以该线程落地的 `create_note_search_run` 为准。
2. 笔记详情 `note_detail` 扣分项为**预留**,详情 connector 通过接口验证前不得启用。
3. 定价数字(积分单价、扣分表、赠送额度、充值面额)最终以公司拍板为准;代码中全部走配置,不写死。
