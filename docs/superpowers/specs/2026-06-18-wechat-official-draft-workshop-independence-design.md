# 微信公众号草稿工坊独立化设计：草稿工坊只存草稿，不再承载公众号帖子候选

## 1. 背景

当前微信公众号链路里有两个语义被混在了一起：

1. **内容库**：承载公众号文章、候选、分析状态。
2. **草稿工坊**：承载可编辑、可保存、可 dry-run 的草稿本体。

现状代码里，公众号文章进入草稿工坊时仍然保留了来源引用和映射关系，例如：

- `AiDraft.source_note_id`
- `WechatOfficialDraftSource`
- 从内容库文章直接生成草稿时的来源联动
- 前端把“候选文章”与“草稿”展示在同一语义链路里

这导致产品语义混乱：

- 用户以为自己在草稿工坊里操作的是草稿，实际上看到的是公众号帖子候选的延伸。
- 删除内容库文章时，草稿的存活语义不清晰。
- 草稿工坊不再像“草稿箱”，而像“文章候选池 + 二创输出”。

用户已经明确要求：**草稿工坊应该存的是草稿，不是公众号帖子，并且不保留来源引用。**

## 2. 设计目标

本轮只做一件事：把公众号草稿工坊改造成真正的草稿箱。

完成后应满足：

1. 草稿工坊只展示和管理 `AiDraft` 草稿本体。
2. 从公众号内容库生成草稿时，生成的是独立草稿副本，不保留来源引用。
3. 草稿一旦生成，不再依赖内容库文章存在与否。
4. 删除公众号内容库文章，不影响已经生成的草稿。
5. 草稿的编辑、复制、dry-run、发送前校验，都以草稿本体为准。
6. 前端不再把公众号文章候选伪装成草稿。

## 3. 设计原则

- **草稿独立**：草稿是可编辑产物，不是文章索引。
- **断开引用**：生成后不再保存来源文章 ID 或来源映射。
- **最小改动**：优先保留现有 `AiDraft` 表，不引入新表。
- **语义优先**：界面和接口命名必须优先表达“草稿”，不能继续强化“帖子候选”。
- **不追溯原文**：本轮不保留来源引用，也不设计回跳到原帖的入口。

## 4. 当前相关事实

现有代码里，相关实现分布如下：

- [backend/app/services/wechat_official_draft_service.py](../../../../backend/app/services/wechat_official_draft_service.py)
  - `create_draft_from_article()` 直接从文章生成草稿。
  - 目前会写入 `WechatOfficialDraftSource`。
  - 当前 `serialize_draft()` 仍输出 `source_note_id`。
- [backend/app/api/platforms/wechat_official/content_library.py](../../../../backend/app/api/platforms/wechat_official/content_library.py)
  - 内容库提供 `/{article_id}/create-draft`。
- [backend/app/api/drafts.py](../../../../backend/app/api/drafts.py)
  - 通用草稿接口仍支持 `source_note_id`，且复制草稿时会保留这个字段。
- [backend/app/models/ai.py](../../../../backend/app/models/ai.py)
  - `AiDraft` 目前有 `source_note_id`。
- [frontend/src/types/index.ts](../../../../frontend/src/types/index.ts)
  - `Draft` 类型仍有 `source_note_id`。
- [frontend/src/pages/wechat-official/wechat-official-dashboard.tsx](../../../../frontend/src/pages/wechat-official/wechat-official-dashboard.tsx)
  - 页面里还有“候选库 / 草稿 / dry-run”混合的表达。

## 5. 方案选择

### 方案 A：保留现有 `AiDraft`，但对公众号草稿彻底断开引用

这是推荐方案。

做法：

- 公众号内容库生成草稿时，只复制标题、正文、标签和必要素材。
- 不创建 `WechatOfficialDraftSource`。
- 不再设置或返回 `source_note_id`。
- 草稿页面只围绕 `AiDraft` 工作，不再依赖内容库文章对象。
- 删除内容库文章后，草稿完全保留。

优点：

- 改动最小。
- 语义立刻变正确。
- 不需要做表结构迁移。
- 风险低，适合当前修正目标。

缺点：

- 历史数据里可能还残留旧引用，需要一次性清理。

### 方案 B：新建公众号专用草稿表

做法：

- 为公众号草稿单独建表，和通用草稿完全分离。

优点：

- 长期语义最干净。

缺点：

- 需要迁移、双写或重构接口。
- 本轮修正范围会明显扩大。

### 方案 C：保留来源字段但仅前端隐藏

不采用。

原因：

- 这只是遮盖问题，不是解决问题。
- 用户已经明确要求“不保留引用”。

## 6. 最终设计

采用 **方案 A**。

### 6.1 数据语义

公众号草稿只保留草稿自身字段：

- `id`
- `platform`
- `title`
- `body`
- `tags`
- `created_at`

对公众号草稿来说，**不再依赖**：

- `source_note_id`
- `WechatOfficialDraftSource`
- 内容库文章对象
- 内容库文章 ID 回跳

如果基础 `AiDraft` 表里仍保留 `source_note_id` 供其他平台复用，则公众号草稿创建时必须显式写空，不返回、不展示、不参与业务逻辑。

### 6.2 服务层

修改 `backend/app/services/wechat_official_draft_service.py`：

- `create_draft_from_article()` 仍然允许从内容库文章“生成草稿”，但生成后是**独立副本**。
- 不再创建 `WechatOfficialDraftSource`。
- `serialize_draft()` 不再输出 `source_note_id`。
- 如有需要，草稿正文仍可保留“改写参考”文本，但这只是内容输入，不是持久来源关系。
- 内容库侧是否继续维护 `analysis.pool_status`，只按内容库自身语义决定；本设计不再把它作为草稿工坊的数据依赖。

### 6.3 公众号链路范围

本轮**不改**通用 `backend/app/api/drafts.py` 的 XHS 草稿语义，也不要求其他平台放弃 `source_note_id`。

本轮只要求公众号链路满足：

- `wechat_official` 的创建草稿流程不保留来源引用。
- `wechat_official` 的草稿响应不展示来源引用。
- `wechat_official` 的前端不再依赖来源引用来判断草稿归属。

### 6.4 内容库接口

修改 `backend/app/api/platforms/wechat_official/content_library.py`：

- `/{article_id}/create-draft` 仍可保留为“从文章生成独立草稿”的入口。
- 但这个入口只做副本生成，不再把草稿和文章绑定成可追溯关系。
- 内容库删除文章后，不需要再处理草稿回收。

### 6.5 前端

修改 `frontend/src/pages/wechat-official/wechat-official-dashboard.tsx` 和类型定义：

- 草稿页只展示草稿，不把内容库候选当作草稿列表的一部分。
- 删除“草稿工坊里显示候选帖子”的混合语义。
- 文案上明确：
  - 内容库 = 文章候选池
  - 草稿工坊 = 草稿箱
- 前端类型 `Draft` / `WechatOfficialDraft` 不再依赖 `source_note_id` 进行页面逻辑。

## 7. 数据清理策略

本轮需要考虑历史残留数据，但不做大规模迁移。

处理原则：

1. 新生成的公众号草稿不再写引用。
2. 历史草稿中如果有 `source_note_id` 或 `WechatOfficialDraftSource`，后续页面不要再依赖它。
3. 如测试需要，可在数据库层做一次性清理脚本或测试工厂修正，但不引入正式迁移表。

## 8. 错误处理

- 如果内容库文章被删除，已生成草稿仍应可正常打开、编辑、dry-run。
- 如果草稿创建时内容库文章不存在，应直接报错，不生成半成品草稿。
- 如果前端请求草稿详情返回了来源字段，前端应忽略，而不是继续展示来源跳转。

## 9. 测试设计

至少覆盖以下场景：

1. 从内容库文章生成公众号草稿后，草稿可独立存在。
2. 删除内容库文章后，草稿仍存在且可读取。
3. 公众号草稿响应不再包含来源引用字段。
4. 公众号草稿复制不会恢复来源引用。
5. 公众号草稿工坊列表只展示草稿，不再混入内容库候选。
6. 前端页面文案和数据展示不再暗示草稿是帖子候选。

## 10. 对用户体验的影响

这次调整会把公众号平台的认知边界拉直：

- 用户在内容库里处理的是“文章”。
- 用户在草稿工坊里处理的是“草稿”。
- 生成草稿后，用户不需要再理解“这个草稿到底算帖子还是草稿”。
- 删除内容库文章不会让用户担心草稿丢失。

这是一个语义修复，不是功能扩张。

## 11. 非目标

本轮不做：

- 不新建公众号专用草稿表。
- 不做数据库迁移。
- 不做内容库到草稿的双向引用体系。
- 不做原帖回跳。
- 不做发布策略调整。
- 不改造 XHS 草稿逻辑。

## 12. 完成标准

满足以下条件即可认为本设计落地完成：

1. 公众号草稿只表示草稿，不再表示帖子候选。
2. 公众号生成草稿后不再保留来源引用。
3. 删除公众号内容库文章不会删除已生成草稿。
4. 公众号前端草稿工坊不再混用内容库数据。
5. 回归测试通过，且用户能直观看到“草稿工坊 = 草稿箱”的语义。

## 13. 自审结果

- 没有遗留 `TBD` / `TODO`。
- 设计目标与用户要求一致：**不要保留引用**。
- 方案聚焦在语义修复，没有扩张成数据库重构。
- 已明确内容库与草稿工坊的职责边界。
- 已明确历史数据只做兼容，不做迁移爆破。
