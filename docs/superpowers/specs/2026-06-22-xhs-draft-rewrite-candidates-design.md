# 小红书草稿工坊 AI 改写候选区设计

> 归档说明（2026-07-22）：本文记录首版页面会话态方案。关于“候选不持久化、刷新后可丢失、采纳不立即保存”的约定已经失效，当前实现与后续修改以 [小红书草稿工坊改写候选持久化设计](./2026-07-22-xhs-draft-rewrite-persistence-design.md) 为准。

## 背景

草稿工坊的核心使用场景是：中间编辑区作为当前草稿操作台，右侧 AI 改写区生成候选版本，用户对比原文和候选后再决定是否采纳。

当前实现中，点击 AI 改写后会直接把生成结果写回中间编辑区，导致用户无法保留原文并对比不同改写模式。这破坏了“先生成候选、再采纳”的工作流。

## 目标

- 中间编辑区只展示当前草稿内容，不被 AI 改写自动覆盖。
- 右侧 AI 区按模式保存候选结果。
- 三种改写模式各自保留当前页面会话内的最近一次生成结果。
- 只有用户点击“采纳”时，候选结果才覆盖中间编辑区。
- 页面刷新后候选结果可以丢失，不做数据库持久化。

## 非目标

- 不新增数据库表或后端版本管理模型。
- 不改变现有 AI 改写接口 `/ai/rewrite-note`。
- 不改变发布中心、保存草稿、标题生成、标签生成流程。
- 不做跨页面刷新后的候选恢复。

## 当前根因

文件：`frontend/src/pages/platforms/xhs/xhs-draft-workbench.tsx`

当前 `handleRewrite()` 流程：

1. 保存中间编辑区当前内容到草稿。
2. 调用 `rewriteDraftWithAi()` 生成改写内容。
3. 立即调用 `controller.setTitle()`、`controller.setBody()`、`controller.setTags()`。

第 3 步直接覆盖中间编辑区，是本次交互回归的根因。

## 推荐方案

采用前端页面会话态缓存候选结果。

### 状态结构

在 `XhsDraftsPage` 内增加按草稿与模式区分的候选缓存。

建议概念结构：

```ts
type RewriteCandidate = {
  title: string;
  body: string;
  tags: { id?: string; name: string }[];
  generatedAt: number;
};

type RewriteCandidateMap = Partial<Record<RewriteTemplateKey, RewriteCandidate>>;
```

实际实现可以只按当前选中草稿维护一份 `RewriteCandidateMap`。当 `selectedDraft.id` 变化时清空候选，避免 A 草稿候选误显示到 B 草稿。

### 生成流程

点击当前模式的生成按钮时：

1. 如果没有选中草稿，直接返回。
2. 设置 `isRewriting = true`。
3. 保存中间编辑区当前内容到后端，让 AI 以最新草稿为输入。
4. 调用 `rewriteDraftWithAi({ draft_id, instruction })`。
5. 将返回的 `title/body/tags` 写入当前 `rewriteTemplate` 的候选缓存。
6. 不修改 `controller.title/body/tags`。
7. 提示“已生成候选，点击采纳后才会覆盖中间草稿”。

### 切换模式流程

点击模式按钮时：

1. 更新 `rewriteTemplate`。
2. 更新 `instruction` 为该模式默认指令。
3. 右侧候选展示区读取该模式缓存：
   - 有候选：显示候选标题和正文。
   - 无候选：显示空状态，提示生成该模式候选。

### 采纳流程

点击候选结果的“采纳”时：

1. 读取当前模式候选。
2. 调用：
   - `controller.setTitle(candidate.title)`
   - `controller.setBody(candidate.body)`
   - `controller.setTags(candidate.tags)`
3. 不立即调用后端保存，保持和当前中间编辑区编辑语义一致：采纳只是写入编辑区，用户仍可继续编辑，再用现有保存或送发布中心流程持久化。
4. 提示“已采纳到中间编辑区，请检查后保存”。

### 放弃流程

点击候选结果的“放弃”时：

1. 清空当前模式候选。
2. 不影响中间编辑区。
3. 不影响其他模式候选。

## UI 设计

右侧 AI 区保持现有布局，改成更明确的候选区：

- 模式按钮仍为：安全改写、轻度润色、种草增强。
- 主按钮文案使用模板里的 `buttonLabel`，例如“生成安全改写版”。
- 生成结果显示为一个 Card：
  - 标题：`改写结果 · 安全改写`
  - 内容：候选标题、候选正文。
  - 操作：`采纳`、`放弃`。
- 空状态：`当前模式还没有候选，生成后可和中间草稿对比。`

## 用户影响

- 用户可以保留中间原文，不会因为试一次 AI 改写就丢失当前版本。
- 用户可以在三种改写模式之间来回对比，选择最合适的版本。
- “采纳”成为明确的意图边界，降低误覆盖风险。
- 页面刷新后候选丢失，符合当前需求，也避免引入复杂版本管理。

## 测试策略

遵循 TDD，先写失败测试再改实现。

前端测试重点：

1. 生成改写候选后，不调用中间编辑区的 `setTitle/setBody/setTags`。
2. 当前模式候选可以显示在右侧。
3. 切换模式不会丢失其他模式候选。
4. 点击“采纳”才调用 `setTitle/setBody/setTags`。
5. 点击“放弃”只清空当前模式候选。

如果现有项目没有 React 测试框架覆盖该页面，则优先提取一个纯函数/小组件承载候选状态逻辑，并用轻量 TypeScript check 脚本锁定行为；再做手动浏览器验证。

## 验收标准

- 中间编辑区原文 A 存在。
- 生成“安全改写”候选 B 后，中间仍是 A。
- 生成“轻度润色”候选 C 后，中间仍是 A。
- 切回“安全改写”后，右侧仍显示 B。
- 点击 B 的“采纳”后，中间才变成 B。
- 放弃某模式候选不影响中间内容，也不影响其他模式候选。
- 刷新页面后候选可以丢失。
