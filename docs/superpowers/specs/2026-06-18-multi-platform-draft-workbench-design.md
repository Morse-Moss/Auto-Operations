# 多平台草稿工作台共享骨架设计

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把公众号草稿工坊和小红书草稿页统一成一个可复用的多平台三栏草稿工作台骨架，让公众号、XHS 以及未来平台都能接入自己的草稿数据源与动作。

**Architecture:** 抽出平台无关的草稿工作台壳，统一提供左侧列表 / 中间编辑器 / 右侧 AI 助手的布局与状态管理；平台差异通过适配器注入，包括草稿列表、草稿详情、保存、dry-run、从源内容生成草稿等能力。公众号只接自己的草稿数据，不再复用内容库候选列表；XHS 保持现有语义，但改为接入同一个工作台骨架。

**Tech Stack:** React, Vite, TypeScript, Ant Design, React Router, FastAPI, SQLAlchemy, pytest.

---

## 1. 背景

当前系统里存在两套草稿相关体验：

- 小红书有一套完整的草稿工作台，已经具备左侧列表 / 中间编辑器 / 右侧 AI 助手的操作形态。
- 公众号草稿工坊虽然已经改成了独立草稿箱，但前端语义仍然是一个平台特例，不适合未来多平台扩展。

用户明确要求：

1. 公众号草稿工坊要“搬成”小红书那种三栏草稿工作台体验。
2. 未来还会接更多平台，所以不能再做一个公众号专用页。
3. 公众号草稿必须保持独立草稿语义，不再依赖内容库候选。
4. 共享的是工作台骨架，不共享错误的业务语义。

## 2. 设计目标

本轮目标是建立一个**多平台草稿工作台骨架**，满足：

1. 公众号、XHS、未来平台都能使用同一套工作台结构。
2. 左侧列表、中央编辑、右侧 AI 助手成为共享布局能力。
3. 平台能力通过适配器暴露，不把平台差异写死在页面组件里。
4. 公众号草稿区显示独立草稿，不再显示内容库候选。
5. XHS 继续保留现有草稿语义，但迁移到共享骨架下。
6. 新平台接入时只需补平台适配器，不需要复制整页。

## 3. 设计原则

- **骨架共享，语义分离**：共享的是布局、状态和页面框架，不共享错误的数据源。
- **平台适配优先**：平台差异集中到 adapter，不散落在 UI 里。
- **草稿优先**：草稿工作台只处理草稿，不把候选文章/笔记伪装成草稿。
- **可扩展**：未来新增平台时，尽量只增加适配器和少量平台文案。
- **最小破坏**：XHS 保留现有行为和数据语义，先迁移结构，再视情况优化交互。

## 5. 方案选择

### 方案 A：复制 XHS 草稿页到公众号，再分别维护

不采用。

优点：
- 快。

缺点：
- 未来平台继续扩展时会产生多份重复代码。
- UI / 交互 / 状态容易再次分叉。
- 公众号和 XHS 会重新长成两套“看起来像但实际上不同”的页面。

### 方案 B：抽共享三栏工作台骨架，公众号和 XHS 各自接适配器

推荐方案。

优点：
- 一套布局，多平台复用。
- 平台差异集中在 adapter 和少量平台文案。
- 未来新增平台时扩展成本低。
- 公众号和 XHS 都能沿用同一套操作台心智。

缺点：
- 第一阶段重构成本高于直接复制。

### 方案 C：先做公众号专用共享壳，后续再抽成多平台骨架

不采用。

原因：
- 等于先做一次局部重构，之后还要再做一次真正抽象，重复成本高。

## 6. 最终设计

采用 **方案 B**。

### 6.1 共享工作台骨架

抽出一个平台无关的工作台壳，统一包含：

- 左侧：草稿列表
- 中间：草稿内容 / 编辑器
- 右侧：AI 助手
- 顶部：平台标题、状态、关键动作

这个壳负责：

- 布局
- 当前草稿选中态
- loading / empty / error 的统一样式
- 三栏区域的基础交互框架

它不负责：

- 具体平台的数据来源
- 是否允许从源内容生成草稿
- 真实发布是否 blocked
- AI 助手具体提示词

### 6.2 平台适配器

每个平台提供一个草稿适配器，负责定义该平台的行为：

- `listDrafts()`
- `getDraft(id)`
- `updateDraft(id, patch)`
- `runDryRun(id)`
- `createDraftFromSource(...)`
- `getAssistantHints(draft)`
- `getEmptyState()`
- `getDraftLabels()`

适配器决定：

- 左栏显示什么
- 中栏能编辑什么
- 右栏开放哪些 AI 操作
- 空态、错误态和按钮文案是什么

### 6.3 公众号接入方式

公众号进入共享工作台后：

- 左侧列表来源是**独立草稿列表**
- 中间编辑器编辑的是**公众号草稿本体**
- 右侧 AI 助手只围绕公众号草稿内容工作
- 不再出现内容库候选卡作为草稿列表
- 不再依赖 `source_note_id`

公众号仍然可以支持“从内容库文章生成草稿”，但生成后的草稿必须是独立草稿，不保留引用关系。

### 6.4 XHS 接入方式

XHS 继续保留现有草稿语义，只是切换到共享工作台壳：

- 左侧草稿列表
- 中间草稿编辑
- 右侧 AI 助手
- 现有草稿类型、保存、改写、发布约束继续沿用

### 6.5 新平台接入方式

未来新增平台时，只需要：

1. 增加平台草稿适配器
2. 提供平台文案与能力矩阵
3. 绑定平台草稿 API
4. 复用共享工作台壳

这能避免再次复制一个“公众号专用页”或“XHS 专用页”。

## 7. 数据流设计

### 7.1 页面启动

进入某个平台的草稿工作台时：

1. 根据 platform id 选择适配器。
2. 拉草稿列表。
3. 如果有默认选中项，拉草稿详情。
4. 拉平台能力配置，决定哪些按钮显示。

### 7.2 左侧列表

左侧列表只负责“选中草稿”：

- 标题
- 创建时间
- 状态标签
- 选中高亮

它不关心草稿来源是文章、笔记、链接还是模板。

### 7.3 中间编辑器

中间编辑器只负责当前草稿本体：

- 标题
- 正文
- 标签
- 平台专属字段
- 平台允许的附件或辅助字段

编辑动作先落到页面状态，再通过保存动作同步到后端。

### 7.4 右侧 AI 助手

右侧 AI 助手面板负责平台相关的辅助动作：

- 改写
- 风格调整
- 标题建议
- 结构优化
- dry-run 校验

不同平台只展示自己允许的按钮。

### 7.5 保存与刷新

保存后：

- 更新当前草稿详情
- 刷新左侧列表摘要
- 不整页硬刷，避免打断编辑

### 7.6 从源内容生成草稿

如果平台支持从源内容生成草稿：

- 通过适配器发起
- 生成后自动选中新草稿
- 回到共享工作台继续编辑

## 8. 平台能力与边界

### 8.1 能力矩阵

每个平台需要声明自己的能力：

- 是否有草稿列表
- 是否支持从源内容生成草稿
- 是否支持 AI 改写
- 是否支持 dry-run
- 是否支持保存标签
- 是否支持附件 / 图片
- 是否支持真实发布

UI 只根据能力矩阵显示按钮，不在组件里硬编码平台分支。

### 8.2 公众号边界

公众号在共享工作台里的边界是：

- 独立草稿箱
- 独立草稿
- 支持编辑、改写、dry-run
- 支持从内容库文章生成独立草稿
- 不展示文章候选列表
- 不保留来源引用
- 真实发布保持 blocked

### 8.3 XHS 边界

XHS 保持现有草稿语义：

- 现有草稿编辑和改写流程继续可用
- 通用 `Draft` 类型不改
- 现有发布限制不改

### 8.4 必须禁止的事

- 用内容库候选直接冒充草稿列表
- 让草稿 UI 依赖 `source_note_id`
- 让不同平台共用一套硬编码按钮集合
- 让共享骨架里混入具体平台业务逻辑

## 9. 组件拆分建议

建议拆成以下几个单元：

### 9.1 `DraftWorkbenchShell`
只负责三栏布局和顶部区域。

### 9.2 `DraftWorkbenchListPanel`
左侧列表面板，只管展示与选中。

### 9.3 `DraftWorkbenchEditorPanel`
中间编辑器面板，只管展示和编辑草稿内容。

### 9.4 `DraftWorkbenchAssistantPanel`
右侧 AI 助手面板，只管平台允许的 AI / dry-run 操作。

### 9.5 `useDraftWorkbench`
统一草稿工作台状态钩子。

### 9.6 `DraftWorkbenchAdapter`
平台适配器接口，用于连接不同平台的数据和能力。

## 10. 错误处理

- 草稿列表加载失败时，显示平台级错误态，不展示旧列表假装成功。
- 草稿详情加载失败时，保留列表，编辑区显示错误说明。
- 保存失败时，明确告诉用户当前草稿未保存成功。
- dry-run 失败时，明确提示阻断原因，不要把错误包装成成功。
- 平台能力缺失时，隐藏按钮而不是点了再报错。

## 11. 测试设计

至少覆盖：

1. 公众号草稿工作台展示独立草稿列表，而不是内容库候选列表。
2. XHS 仍能在共享工作台壳下正常渲染自己的草稿内容。
3. 工作台根据平台能力隐藏不支持的按钮。
4. 草稿加载失败不会把旧草稿当作当前内容继续展示。
5. 公众号草稿不再依赖 `source_note_id`。
6. 新平台适配器可以在不改共享壳的前提下接入最小草稿列表。

## 12. 对用户体验的影响

这次重构后，用户会感知到：

- 不同平台的草稿都在一个熟悉的三栏工作台里。
- 公众号和 XHS 的操作方式一致，但语义仍然各自独立。
- 以后新增平台时，用户不需要重新学一套全新的草稿页。
- 公众号草稿不会再和内容库候选混在一起。

## 13. 非目标

本轮不做：

- 不统一所有平台的后端草稿表结构。
- 不改造 XHS 的业务规则。
- 不新增真实发布能力。
- 不做平台间草稿迁移。
- 不改内容库页面语义。

## 14. 完成标准

满足以下条件即可认为本设计成立：

1. 有共享的三栏草稿工作台骨架。
2. 公众号和 XHS 都能接入该骨架。
3. 公众号显示独立草稿，不再显示候选文章。
4. 平台能力通过适配器控制，而不是页面硬编码。
5. 未来新增平台时无需复制整页。
