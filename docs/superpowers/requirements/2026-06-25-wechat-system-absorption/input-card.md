# 公众号系统完整吸收输入卡

## 背景

当前主系统是 `XHS_ALL_IN_ONE` Web-first 平台，公众号模块已经具备基础表、登录会话占位、账号/文章/指标/评论/快照/内容库/草稿/Redfox 配置与采集接口。近期 Redfox 文章详情接口出现持续 SSL 断连，暴露出当前公众号模块过度依赖单一第三方详情源的问题。

用户要求：把已下载的公众号获取系统功能完整吸收到当前主系统，而不是只修 URL 导入。

## 目标用户

- 当前主系统操作者：需要围绕小红书与公众号做内容发现、素材沉淀、热点拆解和二创草稿。
- 运营/内容团队：需要稳定获取公众号文章、正文、图片、数据指标和历史文章，用于选题与复用。

## 业务目标

1. 公众号模块从 Redfox 单一增强源，升级为多源公众号内容获取系统。
2. 支持从公众号后台/微信文章页面/RSS/Redfox 等来源采集文章。
3. 让公众号内容进入统一内容库、分析、草稿工坊和飞书协作链路。
4. 降低第三方接口不可用时对核心工作流的影响。

## 初始范围：按“完整功能”理解

纳入评估的功能：

- 公众号登录/凭证管理
- 公众号搜索与账号信息获取
- 公众号历史文章列表同步
- 单篇文章 URL 获取正文
- 正文 HTML/纯文本/图片提取与快照保存
- 阅读量、点赞、分享、评论、评论回复采集
- RSS 订阅与定时更新
- 导出 HTML/JSON/Markdown/TXT/DOCX/Excel/PDF 的能力评估
- 图片代理/图片下载/防盗链处理
- 代理池、限频、失败诊断、风控状态识别
- 黑名单/分类/标签/收藏/已读等内容管理能力评估
- 外部通知/Webhook/企业微信/飞书通知能力评估
- 级联/多节点采集能力评估

## 明确非目标（第一轮吸收不直接做）

- 不实现绕过微信风控、验证码绕过、批量账号池或高频自动化。
- 不把 AGPL 项目代码直接复制进主系统。
- 不把另一个系统作为新的主入口；主系统入口仍是当前 FastAPI/React 平台。
- 不替换小红书主系统基线。
- 不对真实账号执行高频批量采集；默认低频、可暂停、可诊断。

## 平台与组织约束

- 后端：Python + FastAPI + SQLAlchemy + Alembic。
- 前端：React + Vite + Ant Design。
- 当前数据库已有公众号表，优先扩展现有模型，不另起系统。
- 密钥、Cookie、Token 必须加密保存，不写入代码和文档。
- 微信公众号采集属于平台风控敏感场景，必须低频、可解释、可人工介入。

## 初始成功标准

- 用户可以在主系统内完成公众号授权状态管理。
- 用户可以搜索公众号、同步历史文章、导入单篇 URL。
- 文章正文、图片、摘要、作者、发布时间能进入内容库并被分析/草稿模块使用。
- 阅读量、点赞、评论等敏感数据在凭证满足时可采集；凭证不满足时给出明确原因。
- Redfox 不可用时，核心 URL/文章正文获取仍可降级运行。
- 采集失败必须记录可诊断状态，而不是保存空壳或暴露底层 SSL 栈。
