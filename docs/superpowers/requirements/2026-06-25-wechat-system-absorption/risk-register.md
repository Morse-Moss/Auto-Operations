# 公众号系统完整吸收风险登记表

## 风险分级

- P0：会阻断核心交付或导致账号/合规重大风险。
- P1：会显著影响成功率、工期或用户体验。
- P2：可通过降级、提示或后置处理。

## 风险清单

| 风险 | 等级 | 触发场景 | 影响 | 应对策略 | 重估触发 |
|---|---:|---|---|---|---|
| 微信风控/验证页 | P0 | 高频访问、异常 IP、无真实浏览器上下文 | 正文、历史列表、评论/指标采集失败 | 低频队列、状态识别、人工验证提示、浏览器兜底 | 若要求无人值守大批量采集，必须重估 |
| 真实账号授权风险 | P0 | 公众号后台扫码登录、Cookie/token 保存 | 账号安全、授权过期、误操作 | 只保存加密 token/cookie；只读接口优先；真实操作需用户授权 | 若加入发布/群发/自动回复等账号动作，必须重估 |
| AGPL 代码合规 | P0 | 直接复制 wechat-download-api 源码 | 可能触发开源义务 | 不直接拷贝实现；只做行为学习并重写 | 若决定作为内嵌服务发布，必须法务/许可重估 |
| 第三方 Redfox 不稳定 | P1 | SSL EOF、HTTP 502、API 变更 | 爆文/详情能力不可用 | Redfox 降级为 provider；本地 provider 兜底 | 若 Redfox 长期不可用，调整优先级到官方/网页链路 |
| 公众号后台接口变更 | P1 | searchbiz/appmsgpublish/comment 参数或响应变化 | 搜索/历史/指标/评论失效 | Adapter 隔离、合同测试、失败样本保存 | 若接口字段大改，相关阶段重估 |
| 本地 HTTP 抓取成功率不足 | P1 | 微信返回空白、验证页、移动端限制 | URL 正文补全失败 | Chrome-like headers、状态识别、浏览器兜底 | 若 P0 URL 导入成功率 < 70%，提前做浏览器兜底 |
| Playwright/CDP 运行环境复杂 | P1 | Windows、服务器、headless、浏览器 profile | 部署和支持成本提高 | 浏览器兜底作为可选 provider；非默认强依赖 | 若要求服务器无人值守浏览器采集，重估 |
| 数据模型膨胀 | P1 | RSS、标签、导出、任务、provider 状态同时落表 | 迁移复杂、影响当前主线 | P0/P1 先用现有表+raw_json；稳定后结构化 | 若要多人协作和长期查询统计，新增表重估 |
| 图片防盗链 | P2 | mmbiz 图片在前端或导出中无法展示 | 内容库预览/导出不完整 | 保存原图 URL；后续图片代理/本地化 | 若导出高保真是上线硬需求，提前做图片代理 |
| 阅读量/评论凭证门槛 | P2 | 缺 pass_ticket/wap_sid2/key 等 credential | 指标和评论采集不可用 | 前端准备项提示、Credential 状态页 | 若要求无凭证采集敏感数据，不承诺 |
| 任务失败不可诊断 | P1 | 多 provider 链路失败但只返回泛化错误 | 用户无法行动 | 统一 error_kind、provider diagnostics、可重试动作 | 若出现 2 次以上未知失败，补诊断优先级提高 |
| 与小红书主系统目标偏移 | P1 | 把公众号模块做成独立 RSS 产品 | 主系统复杂化、交付失焦 | 保持“公众号内容服务于小红书选题/草稿”定位 | 若要求独立公众号 RSS SaaS，另立项目重估 |

## 风险池建议

- P0/P1 阶段：基础开发估算外增加 30%-40% 风险池。
- P2/P3 阶段：基础开发估算外增加 25%-35% 风险池。
- 如果要求真实浏览器无人值守和高成功率采集，风险池提升到 50%+。

## 边界声明

本方案不实现验证码绕过、风控规避、账号池、高频自动化。系统只做低频、可授权、可诊断的采集与内容管理。
